Limitations de l'audit

La connexion directe PostgreSQL est impossible depuis l'environnement d'audit (DNS ne resout qu'en IPv6, sandbox IPv4-only). Par consequent, certains elements necessitent une verification complementaire via le Dashboard Supabase.

Section 7
Analyse Multi-Tenant
L'isolation multi-tenant repose sur la colonne tenant_id presente dans la plupart des tables. L'objectif est de s'assurer qu'aucun utilisateur du tenant A ne peut acceder aux donnees du tenant B, meme en appelant directement l'API Supabase.

FAILLE CRITIQUE : event_assignments sans tenant_id

La table event_assignments lie un evenement a un utilisateur mais n'a pas de colonne tenant_id. Cela signifie : (1) Impossible d'appliquer une RLS basee sur tenant. (2) Un utilisateur du tenant A pourrait theoriquement voir les assignations d'evenements du tenant B. (3) La jointure avec events.tenant_id est necessaire pour filtrer, mais la RLS ne peut pas faire ca directement.

Action requise : Ajouter tenant_id uuid NOT NULL REFERENCES tenants(id) + index.

Plan de migrations (non-destructives)
Toutes les migrations proposees sont non-destructives et preservent integralement les donnees existantes. Elles doivent etre executees dans l'ordre numerique.
Migration 001 — Correction critique : tenant_id sur event_assignments
ALTER TABLE event_assignments ADD COLUMN tenant_id uuid NOT NULL DEFAULT '00000000-0000-0000-0000-000000000000'::uuid; UPDATE event_assignments ea SET tenant_id = e.tenant_id FROM events e WHERE ea.event_id = e.id; ALTER TABLE event_assignments ALTER COLUMN tenant_id DROP DEFAULT; ALTER TABLE event_assignments ADD CONSTRAINT fk_event_assignments_tenant FOREIGN KEY (tenant_id) REFERENCES tenants(id); CREATE INDEX idx_event_assignments_tenant_id ON event_assignments(tenant_id);
Migration 002 — Contraintes CHECK
ALTER TABLE users ADD CONSTRAINT chk_user_role CHECK (role IN ('root_admin','firm_admin','lawyer', 'secretary','collaborator','accountant','trainee')); ALTER TABLE cases ADD CONSTRAINT chk_case_status CHECK (status IN ('new','open','in_progress', 'pending','closed','archived')); ALTER TABLE invoices ADD CONSTRAINT chk_invoice_status CHECK (status IN ('draft','sent','paid', 'overdue','cancelled')); ALTER TABLE events ADD CONSTRAINT chk_event_criticality CHECK (criticality IN ('low','normal','high','urgent'));

Section 11
Script SQL a executer dans le Dashboard Supabase
Pour completer l'audit (RLS, triggers, fonctions, index, contraintes existantes), le script suivant doit etre execute dans le SQL Editor du Dashboard Supabase. Le resultat doit etre fourni pour finaliser le rapport.
-- 1. RLS STATUS SELECT relname AS table_name, relrowsecurity AS rls_enabled, relforcerowsecurity AS rls_forced FROM pg_class WHERE relnamespace = 'public'::regnamespace AND relkind = 'r' ORDER BY relname; -- 2. RLS POLICIES SELECT schemaname, tablename, policyname, permissive, roles, cmd, qual, with_check FROM pg_policies WHERE schemaname = 'public' ORDER BY tablename, policyname; -- 3. TRIGGERS SELECT event_object_table AS table_name, trigger_name, event_manipulation, action_timing, action_statement FROM information_schema.triggers WHERE trigger_schema = 'public' ORDER BY event_object_table, trigger_name; -- 4. FUNCTIONS (public schema) SELECT p.proname AS name, pg_get_function_arguments(p.oid) AS args, pg_get_function_result(p.oid) AS returns, prosrc AS source FROM pg_proc p JOIN pg_namespace n ON p.pronamespace = n.oid WHERE n.nspname = 'public' ORDER BY p.proname; -- 5. INDEXES SELECT schemaname, tablename, indexname, indexdef FROM pg_indexes WHERE schemaname = 'public' ORDER BY tablename, indexname; -- 6. CONSTRAINTS (UNIQUE + CHECK) SELECT tc.table_name, tc.constraint_name, tc.constraint_type, cc.check_clause FROM information_schema.table_constraints tc LEFT JOIN information_schema.check_constraints cc ON tc.constraint_name = cc.constraint_name WHERE tc.table_schema = 'public' AND tc.constraint_type IN ('UNIQUE', 'CHECK') ORDER BY tc.table_name; -- 7. ENUM TYPES SELECT t.typname, e.enumlabel, e.enumsortorder FROM pg_type t JOIN pg_enum e ON t.oid = e.enumtypid ORDER BY t.typname, e.enumsortorder; -- 8. STORAGE POLICIES SELECT * FROM storage.policies ORDER BY bucket_id, name;
Section 12
Resume executif
Forces identifiees
  • Architecture multi-tenant deja en place avec tenant_id sur la majorite des tables
  • Systeme d'audit avec chaine de hachage (bien que non active)
  • 14 fonctions RPC couvrant securite, audit, sessions et conformite RGPD
  • Tables de securite (sessions_log, rate_limit_buckets, csp_violations)
  • Isolation des documents par tenant dans le Storage
  • Donnees de demonstration preservees (8 utilisateurs, 3 tenants, 35+ entrees d'audit)
Faiblesses critiques
  • event_assignments sans tenant_id — faille d'isolation multi-tenant
  • Chaine de hachage d'audit non activee — tous les hashes sont NULL (35/35)
  • MFA a 0% d'adoption — aucun facteur TOTP sur 8 utilisateurs
  • RLS policies non verifiables par API REST — confirmation SQL requise
  • Storage policies non verifiables — API retourne 404
Ameliorations prioritaires (dans l'ordre)
  • 1. Ajouter tenant_id a event_assignments — Migration 001
  • 2. Verifier et renforcer les RLS — Script SQL section 11
  • 3. Activer la chaine de hachage d'audit — Backfill + trigger
  • 4. Ajouter les 17 colonnes manquantes — Migration 003
  • 5. Ajouter les 4 contraintes CHECK — Migration 002
  • 6. Creer les 11 index manquants — Migration 004
  • 7. Definir les Storage policies — A determiner apres verification
  • 8. Deployer MFA pour tous les utilisateurs
Note : Ce rapport a ete genere via l'API REST Supabase. Les elements marques comme non verifiables necessitent une execution du script SQL de la section 11 dans le Dashboard Supabase. Les migrations proposees sont toutes non-destructives et preservent les donnees existantes.
